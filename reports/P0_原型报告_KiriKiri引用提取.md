## 1. 本轮完成的事：9nine 加密脚本补解（收益顺序第①项）

### 1.1 问题定位

- 前人管线按「bo 分段常量 XOR」解密了大部分 `.ks`，但**文本文件没有例外点修复，且尾段密钥经常选错**：实测 `maplist.ks` 正确 kt=0x02，前人选了 0x27 → bo 之后全文乱码 → 引用提取不到 → ④ 被低估、5 款 9nine 被迫整游戏保守保留。
- 9nine 五章各有 6~25 个脚本处此状态。

### 1.2 解法（三层，按序尝试）

1. **CxEncryption VM**（`peel.py` + `mod_all.json` 方案表；两者均未入库）：春/天色/九次九日匹配到 MOD(518,77) 方案，VM 密钥流直接完美解开大多数顽固文件（freecamera/sysmenu/version/maplist 全部 0 坏字节）。
2. **结构分常量模型**（新章/雪色参数 (0x204,1211) 在 MOD 无条目）：头/尾密钥均以 **KAG 结构分**选取——关键教训：**坏字数对尾段无效**（半角假名永远"合法"），必须用 `[tag]`/`storage=`/ASCII 结构密度打分。
3. **小文件首字节启发式**：bo≥n 的 <512B 小文件结构分不可靠，要求解密结果首字节为 `*`/`;`/`[`/`@` 且坏字符≤1（dummy_scene.ks 由此以 kh=0xEA 解开，内容为 `*dummy| シーン回想ダミー @msgoff @endrecollection`，**零引用存根**）。

### 1.3 附带修复的解码器缺陷（`ks_refs.py`）

| 缺陷 | 现象 | 修法 |
|---|---|---|
| 纯 SJIS 用严格解码 | 已解密文本带 2 个未修例外点 → 整文件判"解不动" | 全部改 `errors='replace'` |
| 结构分只认 `[tag]` | KAG3 的 `@macro` 调用、数据表型脚本被拒 | 打分纳入 `[@\[]`、`text=`/`name=` 等 |
| UTF-8 乱码候选凭顺序胜出 | SJIS 字节被 UTF-8 解成乱码但保留 ASCII 结构分，持平又优先 → 好候选被挤掉 | 坏字符>5% 的候选**按候选**出局（不能只守卫最终获胜者） |
| 无 BOM UTF-16LE 漏检 | 9nine 部分脚本 | 高位字节 0x00/0x30 占比≥50% 才认 |

### 1.4 结果

- **52 个脚本修复，0 失败**；9nine 五章全部达到「0 解不动」→ 全部可测算。
- 新章 ④ 从 0.29 → 0.61 GB（新解开的系统脚本确实引用了资源）。
- 输出到各 `<游戏>_脚本修复/` 目录（**未改动原解包目录**），`ks_refs.py` 解不动时自动回退读取。

## 1-B. 收益顺序第②项：消未命中引用 + 动态映射防误裁

### 做法（`ks_refs.py` 的 `parse_refs` / `dynamic_candidates`）

1. **噪声消除**（未命中引用 301→145 的主力）：
   - **注释行整行跳过**——KAG 里 `;` 开头的行是作者注掉的旧代码（`file=chi_0_d_103` 就藏在这里）
   - **去掉 `layer=` 属性**——`layer=message0/stage` 是图层名不是资源
   - **纯数字值跳过**——`[se storage="5000"]` 是音效 ID 不是文件（夏空彼方一项就 505 个）
   - **脚本装载标签过滤**——`[jump]/[call]/[addSysScript]/[addSysHook]` 的 storage 是 `.ks` 目标
   - **`%参数|默认值` 取默认值**——KAG 宏默认参数常是真资源（`%file|bg_c_white` → `bg_c_white`）
   - **`／`(U+FF0F) NFKC 保护**——全角斜杠是合法文件名字符，被 NFKC 转成 `/` 会伪造路径分隔符（夏空彼方 59 个日文音效名由此匹配失败）
2. **动态映射防误裁**（本轮最重要的发现）：事件 CG **只经映射 ID 引用**——枯花 `[ev file=ev01a]` → `evimage/Haru_01a.png`，真实文件名 **0 次**出现在脚本里；映射表在引擎/TJS 中，静态不可解。若不处理，这些 CG 会被当"无引用"裁掉（**误裁**）。做法：未命中引用剥常见前缀（`ev`/`e`/`large_`/`bg_`/`cg_`）取核心 token，把"文件名含该 token"的池内文件**全部计入 ④**（宁多勿缺的安全方向）。实测保留 300 个文件 / 0.44 GB，抽查确认 `ev05a` → `haru_05a.png` 等正确命中。
3. **宏展开经评估后放弃**：`storage=&x` 全局仅 8 处且全是 TJS 全局变量/函数（`&tf.start_storage`、`&GetTitleBgmFile`），静态无可恢复量——用数据证伪了"做宏展开"的设想。

### 剩余 145 个未命中的性质（均已核实，非缺陷）

| 类别 | 例 | 处置 |
|---|---|---|
| 动态映射 CG 引用 | `ev01a`/`e101a`（9nine/枯花） | 候选文件已保守保留 |
| 系统占位图未解出 | `black`/`bg_c_white`/`01map`/`cutin_bar` | 解包树里确实没有（引擎程序生成或未解出），报告为准 |
| 影片/配置名 | `OP`/`configback.jpg`/`novelogo` | 同名文件不在池中 |
| 少量剧本数据文件 | `02_kt05_sub01.txt` | 该章文件未提取到 |

## 1-C. 收益顺序第③项前半：G線上の魔王全解锁（v4）

### 结论：「加密」是假象，是前人管线涂出来的

- 归档里 G線 的 `.ks` 就是 **zlib 压缩的明文 Shift_JIS**（data.xp3 115 个 `.ks` 全部可读）。
- 解包目录里的密文副本 = **zlib 压缩段整体 XOR 0x23**（磁盘副本与归档解压原文异或恒为 0x23）。
  前人把「压缩数据的高熵」误判为加密，还涂了一层 0x23 —— **经典误判**。
- `.tlg` 图片未被污染（魔数 `54 4c 47` 完好），受害的只有 `.ks`。

### 解法：`ks_reextract.py` 按归档真实结构重提取

```bash
python tools/ks_reextract.py "G線上の魔王解包"   # 解压段原样落地，不涂任何东西
```
**118/118 全部成功**（116 强解码 + 2 个 `@iscript` 重的文件弱接受），输出到 `G線上の魔王解包_脚本修复/`。

### 顺带修的大漏：无括号 @宏 调用（所有游戏受益）

G線 用自定义宏集且**调用不带括号**（行尾即止），TAG_RE 要求 `]` 收尾所以全漏：
- `@chr c=… l=… r=… ll=… rr=…`（立绘 中/左/右/次左/次右，6402 次）
- `@mface name=…`（差分，1707 次）
- `@ev storage=…`（事件图，514 次）
- `[nm t=… s=…]`（`s=` 是语音，14573 次）

修法：`AT_CALL_RE` 解析无括号调用 + `TAG_EXTRA_ATTRS` 按标签扩展属性（chr/mface/nm）。
效果：G線 引用发现 12 → **16583**，④ 从 0.00 → **0.79 GB（保留率 72.6%）**；9nine（55→131）、枯花（40→116）也跟着翻倍。

### G線 遗留：差分命名映射（已安全保留，未实现精确匹配）

- 引用 `eiichi_a_se_01_b` → 实际文件 `face/st_eiichi_a_se_01b_f.tlg`（`st_` 前缀、差分字母移位、`_f` 后缀）。
- 已由保守保留覆盖（2162 个 / 0.59 GB 计入 ④，安全方向）；精确匹配留待 IR 阶段（需按游戏配命名规则）。

## 5-B. Monkeys!! 脚本加密分析（v4 结论：需二进制级逆向）

**结构已探明**：`.ks` = zlib( 密文 )，密文 = **UTF-16BE 明文、仅低字节（奇位）被流式密码变换**：
- 偶位（高位字节）干净地呈 0x00×5911 / 0x30×2276（ASCII+假名）——未被变换；
- 奇位（低位字节）全范围分布、**无周期性**（自相关 600 周期内无峰，基线 0.08）→ 是流密码不是重复密钥；
- 常量/两位密钥暴力全部失败（合法字符率最高 0.66）；
- MOD 方案表（181 条）无 Monkeys!! 条目，peel.py 的 VM 用不上；
- 前人管线涂的 0x3C 同样是误判产物（disk = 归档解压原文 ^ 0x3C）。

**要继续需要的**：从 `Monkeys!!.exe` / `Monkeys!!_cn.dll` / `BootStrap.exe` 提取该游戏的 cipher/VM 参数（反编译二进制），或找到密钥流生成算法。属于多小时重活，且池仅 2.57 GB——建议排在所有「按款数/体积 ROI 更高」的引擎适配之后。

> 备注：Monkeys!! 的 `_cn.xp3` 是 EnigmaVB 容器（`EVB\0` 魔数），与脚本加密无关，勿在此浪费时间。
